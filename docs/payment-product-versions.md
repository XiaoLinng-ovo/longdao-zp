# 商品版本管理

## 管理员操作

商品后台按商品展示当前版本，同一商品的历史配置放在「历史版本」中，不再因为调价而在主列表重复展示。

| 操作 | 结果 |
| --- | --- |
| 新建商品 | 创建独立商品，初始为下架，确认后可上架。 |
| 编辑并上架 | 修改原商品的配置，先查看差异并确认，再发布该商品的新版本；旧版同时停售。 |
| 复制为新商品 | 将已有配置带入表单，保存为另一独立商品，不替换来源商品。 |
| 历史版本 | 查看历史配置、版本原因和操作人；历史版本不能直接上架。 |
| 以此版本恢复 | 将历史配置带入编辑表单，确认后发布为新的版本，不覆盖历史记录。 |
| 上架或下架 | 只改变当前版本的销售状态，不改变订单和已到账权益。 |

编辑时商品类型不能改变，服务订阅和算力充值不能相互转换。差异确认窗可以返回继续编辑，保留已经填写的内容。失败后可重试；重复提交同一请求不会重复生成版本。其他管理员已发布新版本时，服务端返回冲突，不会覆盖对方修改。

## 整理旧的重复商品

升级不会按名称自动合并商品，既有同名商品仍独立保留。需要整理时：

1. 在当前商品列表勾选 2 至 20 个同类型商品。
2. 点击归并，明确选择哪一条配置保留为当前版本。
3. 明确选择归并后是否在售，并填写归并原因。默认不在售，不根据原状态自行上架。
4. 确认后只保留一条当前商品，其余配置收纳为历史版本，原订单关联不变。

归并是整理商品身份，不是批量改价。归并后历史版本重新编号，原版本 ID 和订单引用不变，审计记录保留归并来源。确认前应检查所选商品确实属于同一个商品系列；系统不会自行判断或执行正式商品归并。

## 历史订单保护

- 商品发布、旧版停售、当前版本指针切换及审计写入在同一个事务完成。
- 价格、权益等配置通过新增版本保存；编辑不覆盖原配置。
- 旧版待付款订单继续使用原订单价格、原权益快照，不能因新版发布而改价或改额度。
- 已到账权益不因发布或归并变化；订单原有退款与核对规则继续生效。
- 历史版本不再接受新下单，但停售本身不取消已经创建的订单。
- 所有后台读写仍检查系统管理员权限，写入仍要求可信来源与 CSRF 验证。

## 数据库与发布

依赖迁移 `0092_payment_product_versions.sql`。该迁移新增商品主记录、当前版本指针、版本信息和发布幂等记录，每条旧商品单独初始化，不改历史订单或企业余额。

正式发布前应备份目标数据库，并按 [数据库升级与 API 发布](database-upgrades.md) 执行：

1. 构建 API 和 Web，确认目标数据库连接及待执行迁移范围。
2. 执行数据库升级并通过迁移门禁检查，再按现有进程管理方式切换新版 API 和前端。
3. 登录系统管理，确认商品列表、历史版本和编辑差异预览可用。
4. 需要整理重复商品时，由管理员在界面逐项确认归并，不自动批量归并。

前端会检查后台返回的商品版本能力标记。API 尚未更新时，商品修改及版本操作暂时不可用，避免新页面调用旧的发布逻辑。直接重启旧 API、仅构建前端或仅更新数据库都不代表整套功能已经上线。
