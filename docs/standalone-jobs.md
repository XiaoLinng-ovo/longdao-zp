# 暂时隐藏招聘需求，支持独立创建岗位

## 当前行为

- “需求管理”侧边栏入口、工作台的新建/导入需求快捷入口及需求审批待办默认隐藏。
- 新建岗位不展示招聘需求选择、不加载招聘需求列表、不发送 `recruitmentRequestId`。
- 即使使用旧链接 `/jobs?create=1&recruitmentRequestId=...`，关闭模块时也不会隐式关联需求。
- 岗位详情以实际存储的关联为准，不再从 URL query 补入关联。
- 岗位名称、部门、招聘人数等基础规则不变。独立岗位仍需创建并确认岗位说明书和 JD，随后可以发布、暂停、恢复和关闭。
- PostgreSQL 中独立岗位的 `jobs.recruitment_request_id` 存储为 NULL；API 为兼容现有前端将其映射为空字符串。原字段已可空，无需数据库迁移。

## 保留历史数据

没有删除需求管理代码、路由、API、需求记录及已有岗位关联。直接使用历史需求 URL 仍可访问（受原权限限制）。历史关联岗位发布时仍检查其需求已审批通过或 converted，不因隐藏模块绕过审批。

## 恢复入口

在 `web/.env.local` 中设置：

```env
VITE_RECRUITMENT_REQUESTS_ENABLED=true
```

然后重启前端开发服务，或重新构建并部署前端。恢复后，新建岗位可以选择关联已审批需求，关联不再强制必填。

默认不设置此变量或设置为 false 即继续隐藏。后端独立岗位支持没有开关，保留对两种岗位模式的兼容。

## 生效与验证

后端修改需由正常的 API 重启流程加载；只刷新页面不会更新已运行的非 watch 后端进程。本次不删除或重写任何现有业务数据。

自动化测试覆盖默认隐藏和开关恢复、新建表单与旧 URL 防关联、API payload、详情发布校验、本地完整岗位流程、PostgreSQL NULL 关联与完整流程/企业隔离。PostgreSQL 测试采用回滚事务，不保留测试数据。
