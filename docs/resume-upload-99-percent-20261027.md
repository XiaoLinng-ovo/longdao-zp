# 简历上传停留 99%：排查与响应恢复修复

日期：2026-10-27，Asia/Shanghai。

**后续已定位公网根因：** 用户提供实际 URL 后，复现旧 QUIC 隧道大请求阻塞，切换新 HTTP/2 隧道验证恢复。详见 `docs/resume-upload-tunnel-20261027.md`。下面保留当时尚未取得 URL 时的排查记录及前端修复范围。

## 已确认的事实

- 旧页面把 XHR 的发送进度强制封顶为 99%，只有收到成功响应才设为 100%。因此 99% 不等于文件剩下 1% 发不出去，而通常是客户端等待 HTTP 响应。
- 旧上传每次请求等待最多 60 秒；超时、网络中断及 502/503/504 后会直接再次发送文件。没有先核对原上传是否已经入库，且页面把具体原因替换为“暂未完成”，不利于定位。
- 排查时，业务库最近三次相关批次项均未进入上传处理：两个 `pending_upload`、一个后续取消，`attempts=0`，没有候选人、申请、简历或解析任务 ID。没有正在执行的数据库查询或锁等待。不能归因于 PDF 解析或 AI 评分。
- 对当前 API 3100 和 Vite 代理 5174 发送相同大小的未授权请求，均能及时得到安全校验响应，说明本地进程并非整体无响应。
- 在独立 PostgreSQL、完整登录/CSRF、真实 Vite 代理与真实浏览器中，782 KiB 合成 PDF 上传正常完成，未复现用户原始网络故障。

**结论边界：已经确定并修复进度展示、错误隐藏和未知结果直接重传的问题；尚不能仅凭截图确认用户原页面是否遭遇隧道、代理、连接中断或特定浏览器网络问题。需要原页面 URL 或新版本显示的具体错误继续定位。** 本次没有降低 CSRF、租户校验或文件校验，也没有单纯加长超时掩盖问题。

## 修改

1. 按实际发送字节显示进度，全部发送后显示“文件已发送 · 等待服务器确认”，与上传入库成功明确区分。
2. 超时、网络错误、处理中冲突和临时网关故障后，先读取原批次项。已入队直接恢复成功；仍在保存则只轮询状态；确认尚未保存才允许重传。
3. 状态接口也不可达时，继续重连确认，不在结果未知时持续重传大型文件。确认请求 5 秒超时、总体仍有最多 5 次重试，可取消。
4. 重试提示保留实际原因和可用的请求编号；网关 HTML 错误能明确标示 HTTP 状态，不再统一隐藏成“暂未完成”。
5. 重试绑定最初账号/企业版本，切换上下文后不继续发送或接受旧企业结果；XHR 重复结束事件只清理和处理一次。
