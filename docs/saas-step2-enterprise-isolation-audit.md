# 第 2 步：企业隔离与权限审计

日期：2026-10-12。状态：代码修复和自动测试完成；第 2 步交付时重启受阻，第 3 步已正常重启新版 API / Worker 并验证企业请求校验。仍不能据此认定可商业化上线。

## 本批修复

1. 面试官选项从全局用户查询改为当前活跃企业成员查询；缺少企业时返回空列表，不降级为全局目录。
2. 统一业务路径企业校验，补齐实时面试、目录、配置等入口。生产 cookie 会话业务请求须携带 X-Workspace-Id，且必须等于服务端已验证会话的企业；该头不选择企业。显式企业管理/认证路径不受旧企业断言约束。Bearer 无头时仍使用会话企业，有头不一致时拒绝。
3. 企业一致性校验置于幂等回放之前；内部幂等键按账号/企业分隔，指纹包含企业、角色、部门。认证和企业切换接口不回放缓存切换结果。
4. 前端业务请求绑定发起时企业/身份修订号；发送前、收到响应后、读取响应体后检查修订号，忽略过期响应，不自动重试误企业写操作。
5. 登录、登出、企业/账号切换通过不含凭证与个人信息的 storage 事件通知其他标签页；旧标签页卸载业务界面并要求刷新，不自动保存或自动刷新表单。重复刷新同一会话不广播、不改变修订号。
6. Offer、薪资版本、入职记录的查询、更新及关联检查增加企业与父记录一致性限制；新增记录显式写入企业。跨企业版本绑定拒绝，历史异常父子归属隐藏而不是自动重分配。
7. 申请、候选人、Offer、入职的 scope 校验不再因没有部门限制而跳过资源存在/企业检查。部门负责人没有部门时，调用 departmentScope 的入口返回 403 DEPARTMENT_SCOPE_REQUIRED，而不是取消部门限制。

| --- | --- | --- |

| 阻断上线 | 钉钉、渠道等配置仍为全局服务；AI 与 Skill 已在第 3 步隔离 | 继续逐批迁移剩余配置，旧全局工具已要求独立平台管理员，但不等于完成租户配置迁移；不得把全局秘密批量复制给客户 |
| 阻断上线 | organization_members.business_role 为空时回退全局 user_roles；新企业 owner 也有此情况 | 设计企业身份与业务能力映射、兼容迁移，不直接默认降权导致所有者失去管理能力 |
| 高 | Offer 写/审批入口的 OFFER_WRITE_ROLES 未包含 approver，审批任务级授权尚不完整 | 单独拆分创建/编辑、审批、发送权限并验证任务授权；不能粗暴把所有写权开放给审批人 |
| 高 | approval_instances/steps 及部分面试子记录写入归属、worker、缓存、文件对象、钉钉回调尚未全面验证 | 链路审计和增量修复，覆盖后台、下载与回调；本批只补足部分入口约束 |
| 高 | 报表、分析结果、后台任务等部门级细粒度限制仍需逐接口复核 | 本批“缺部门拒绝”只覆盖调用 departmentScope 的入口，不代表部门权限完整 |

| 限制 | 开发 NODE_ENV=test 默认放宽 workspace 强制断言，旧内部无组织仓储仍兼容 | 生产不能启用 test 模式；持续阻止未选企业请求降级到全局仓储 |
