# 第 3 步：企业独立 AI 模型配置与提示词 Skill

交付日期：2026-10-12。状态：代码、迁移、重启、自动与运行态只读验收完成，等待用户真实模型验收。不开始第 4 步。

## 本批功能

1. 左侧新增「企业 AI 配置」，显示当前企业名称。仅当前企业所有者 / 管理员可管理，平台全局角色不替代企业管理身份。
2. 地址、API 密钥、模型、超时持久化到 enterprise_ai_settings，每企业独立；模型支持手填。省略密钥保留原值，显式清空需确认。
3. 密钥用 AES-256-GCM 加密，AAD 绑定企业 UUID，固定掩码不透露原文/片段/长度。保存、Skill 写操作在事务中检查企业管理权限，审计不包含配置值或密钥。
4. 写作 Skill 与简历评分 Skill 按企业管理、读取和绑定岗位。外企业及未归属历史 Skill 不展示；损坏跨企业岗位绑定不会泄漏岗位 ID。
5. 岗位说明书、JD、面试题与分析、后台问题表、持久化简历分析链路使用所属企业配置。Worker 从任务、简历、申请、岗位、候选人数据库关系判定归属，不信任 payload.organizationId。
6. 未配置企业 AI 不回落到全局 OPENAI_*。已有明确本地岗位文档回退仍兼容；基本简历解析可不用模型，但指定评分 Skill / 岗位语义要求时明确报 ENTERPRISE_AI_NOT_CONFIGURED，不以默认关键词评分冒充 AI。
7. 模型请求禁止 HTTP 重定向，降低凭证被重定向到其他主机的风险；生产须启用平台 HTTPS origin 白名单。这不是完整 DNS/网络 SSRF 防护审计。

## 主密钥备份与恢复

- 主密钥是 Base64 编码的随机 32 字节，API 与 Worker 必须使用同一值；它与客户供应商 API 密钥是不同东西。
- 本地保存于被 Git 忽略的 .env。安全备份当前主密钥与数据库，备份也不得进入 Git、截图、聊天或公开日志。
- 生产放入密钥管理系统或受限服务器配置，设置真实文件 ACL 与备份访问控制；不要把 Windows chmod 当成充分权限保护。
- 恢复数据库时必须恢复对应主密钥；若主密钥丢失或被替换，已存客户密钥无法解密，需各企业重新填写供应商密钥。
- provisioning 脚本只在缺少主密钥时生成，已存在时保留；不要随意重新生成。密钥版本化轮换与自动重加密尚未交付。
- 新环境操作顺序：API 构建 → 迁移 → provisioning 或注入已有安全备份主密钥 → 启动 API / Worker。不需要 seed。

## 生产接口白名单

在平台环境变量设置 AI_ALLOWED_BASE_URL_ORIGINS，例如 https://api.deepseek.com,https://api.openai.com。此处是精确 origin，不包含 /v1 路径。企业页面可以填允许 origin 下的兼容 API 路径。

NODE_ENV=production 时没有白名单会拒绝企业 AI 调用，只允许 HTTPS。添加供应商须由平台审核；不要向所有客户开放任意主机。开发环境可使用本地 HTTP 兼容模型服务。

旧 LLM_* / OPENAI_* 环境变量仍兼容旧工具，但不是本批企业运行链路的模型来源。FunASR 和钉钉未迁移为企业独立配置。

## 用户验收

1. 刷新页面，以当前企业所有者或管理员进入左侧「企业 AI 配置」。确认顶部企业名称，普通成员应无管理入口。
2. 重新填写本企业接口地址、API 密钥、模型，测试连接并保存。当前企业空配置是隔离后的预期，不表示迁移丢失了旧全局配置。
3. 刷新后地址/模型仍在，密钥不回显；空着密钥仅修改超时并保存，应保留原密钥。清除功能有二次确认，不要为验收清除正式密钥。
4. 创建本企业的岗位文档写作 Skill，在岗位说明书 / JD 生成时选用，检查结果是否遵循规则。实际模型生成尚未代用户执行。
5. 如需简历评分，创建本企业岗位评分 Skill 并绑定测试岗位，以测试简历验收 Worker 语义分析。不得盲目重试历史归属异常任务。
6. 如已有第二企业，切换后应看不到第一企业配置/Skill，也不会默认复制其密钥。当前单企业浏览器不声称已完成双企业 UI 验收；双企业数据隔离由 PG 专项证明。
7. 重启后数据保持由数据库持久化链路测试覆盖；配置真实模型后的再次重启与连通验收由用户确认，避免自动消耗额度。
