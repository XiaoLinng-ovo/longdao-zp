## 一、为什么仍未完成

不能将全部未完成事项归因于用户禁止真实服务。具体有三类：

1. **实施没有收尾。** 已修复对象一致性、流式音频、部分资源归属和空闲等待取消，但统一关停期限、慢存储与心跳公平性、具体服务商只读核对适配仍未完成。局部修复不是原方案全部实现。
2. **验收建设和执行没有完成。** 全业务真实浏览器场景、真实进程反复创建关闭测量、持续负载工具和完整执行尚不齐全。单测多、2000 份短时导入通过、120 分钟合成音频处理通过，都不能替代这些验收。前轮优先处理新发现问题后，未逐项完成原方案验收，这是执行安排的不足。
3. **部分处置需要条件或单独确认。** 服务商必须有可用的只读查询能力；凭据轮换、历史清理等会改变真实环境，仍须确认。长测需要明确本机资源窗口，但正常隔离测试不应一概被解释为缺少用户授权。

本次重新安排的目的不是重复已有优化，而是为每个缺口规定证据和关闭条件。

## 四、实施顺序与阶段门槛

### 第一阶段：隔离底座、关停与资源公平性

1. 统一测试配置入口：显式指定独立 PostgreSQL 实例、受限测试账号、随机测试库、随机端口和专用临时目录；不加载真实环境文件。随机库名本身不构成隔离，启动前还须核对端点、账号权限、目录和清理清单。
2. 对 API、Worker、浏览器及外部边界设出站白名单，只允许已登记本机测试服务；邮件、支付、模型请求由本地替身接收。容器依赖下载另设受控构建阶段，不能因此开放业务测试外呼。
3. 补全统一关停预算：先停止接收和领取，再排空；期限到达时向可取消的 HTTP、存储、子进程和数据库操作传播取消。连接等待、业务执行、清理使用剩余预算，避免每层重新获得完整超时。
4. 不以 Promise.race 提前返回或直接 process.exit 冒充资源回收。无法取消的操作必须报告残余资源及状态；外部推理可能已提交时保持未知，不能标成普通失败自动重试。数据库取消方式先按驱动能力确认，失败时丢弃受影响连接，不能让迟到查询污染复用连接。
5. 组合慢 PUT、连接池上限 1/2、并发简历导入、音频续租、删除、Worker 领取和关闭。记录连接等待、锁等待、续租余量与租约失效。先用证据定位，再选择限流、保留容量或最小资源隔离，不盲目放大连接池或拆掉 advisory lock。
6. 使用真实独立 PG、Node 进程、存储替身及 ffmpeg 做至少 50 次创建/关闭，包括启动失败、重复关闭、慢 IO 和在途取消。记录进程树、连接、句柄、定时器和临时文件；预热后观察趋势，不要求正常缓存 RSS 归零。
7. 租约恢复分别测：修改时间的快速故障测试、缩短但真实等待的测试租约、至少一组实际配置租约自然到期。报告不能混写。

通过条件：停止后不再领取；预定可取消操作在预算内结束；剩余资源逐项列明；无重复有效提交、跨公司数据或误清理；慢存储不导致心跳长期饥饿。存在不可解释残余或持续增长时，不进入长期负载阶段。
