# 内部招聘平台 V1 设计规格

## 1. 目标

将现有单页招聘流程演示重建为可在公司服务器稳定运行的内部招聘平台。系统服务公司内部招聘团队，覆盖招聘需求、审批、岗位与 JD、候选人、AI 简历筛选、面试、Offer、入职归档、运营报表和操作审计。

系统使用已获授权的 CandiSift 作为独立 AI 简历分析服务；主平台始终保有招聘流程、人工决策和业务主数据的控制权。

## 2. 范围

### 包含

- 内部账号登录、角色权限与管理员后台。
- 招聘需求申请、多级审批、撤回、驳回和审批记录。
- 岗位说明书、JD 编辑确认、招聘状态与发布渠道管理。
- 候选人档案、PDF/DOCX/文本简历上传、来源、去重、标签和人才库。
- CandiSift 异步解析、脱敏、岗位匹配、评分、排序、分析报告和人工复核。
- 多轮面试安排、面试官反馈、评分表、面试结论。
- Offer 审批、模板生成、发放、接受/拒绝和入职归档。
- 管理员配置模型、模型密钥、文件存储、邮件/短信、招聘渠道和 AI 调用限额。
- 招聘漏斗、渠道、周期、转化率和 AI 调用成本报表。
- Docker Compose 服务器部署、HTTPS 反向代理、健康检查、备份和审计。

### 不包含

- 薪酬、考勤、绩效、员工自助等完整 HRMS 功能。
- 自动淘汰候选人；任何淘汰、录用和 Offer 决定必须由有权限的人员确认。
- 将模型密钥暴露给浏览器或普通招聘成员。

## 3. 用户与权限

| 角色 | 核心权限 |
| --- | --- |
| 系统管理员 | 账号、角色、模型与密钥、渠道、存储、通知、全局审计和系统健康配置。 |
| HR 管理员 | 全流程查看，设置招聘流程和审批链，审批 Offer，查看报表。 |
| 招聘专员 | 创建需求、维护岗位、导入简历、发起筛选、安排面试和处理 Offer。 |
| 用人部门负责人 | 审批本部门需求、确认岗位说明书/JD、查看本部门候选人与面试结论。 |
| 面试官 | 仅查看被分配的候选人和面试材料，提交面试反馈。 |

服务端对每个动作校验角色、岗位归属和当前流程状态。前端按钮隐藏只用于改善体验，不能作为权限依据。

## 4. 页面与模块

前端使用 Vue 3、TypeScript 和 Vite。所有业务页面使用路由组织，页面不直接保存权威业务状态。

```text
src/
  app/                 应用壳、路由、权限守卫、布局
  modules/
    dashboard/         招聘概览与待办
    requisitions/      招聘需求与审批
    jobs/              岗位说明书、JD、发布渠道
    candidates/        候选人、简历、AI 分析、人才库
    interviews/        面试安排、反馈和评分表
    offers/            Offer、审批和入职归档
    reports/           漏斗、渠道、周期和成本报表
    administration/    用户、角色、模型、密钥、渠道和审计
  shared/              通用 UI、API 客户端、类型、格式化与错误处理
```

每个业务模块拥有 `pages/`、`components/`、`api/`、`types/` 和必要的 `stores/`。弹窗、表格和表单等纯界面组件位于 `shared/`；不得将流程规则写入可复用 UI 组件。

## 5. 后端与运行组件

业务后端使用 TypeScript 模块化单体，推荐 NestJS 搭配 Fastify。它提供认证、授权、参数校验、OpenAPI、后台任务投递和审计钩子。CandiSift 保持 FastAPI 独立服务。

```text
浏览器
  -> Web 前端
  -> 业务 API
       -> PostgreSQL       招聘业务数据、权限、审批、审计
       -> Redis            缓存、异步队列、限流
       -> MinIO / S3       简历与附件
       -> CandiSift API    简历分析任务与结果
       -> 通知适配器       邮件、短信、企业消息
```

业务 API 是唯一可被前端调用的服务。前端不可直接调用模型供应商、对象存储或 CandiSift 的内部管理接口。

## 6. 核心数据模型

| 模块 | 主要实体 | 关键关系 |
| --- | --- | --- |
| 身份权限 | User、Role、Permission、Department | 用户归属部门并拥有角色；所有敏感操作写入 AuditLog。 |
| 招聘需求 | Requisition、ApprovalFlow、ApprovalStep、WorkflowEvent | 一个需求有一条审批流、多条审批记录和不可变状态事件。 |
| 岗位 | Job、JobSpec、JobDescription、PublishChannel、WorkflowEvent | 岗位来源于已通过需求；说明书与 JD 保留版本、确认记录和状态事件。 |
| 候选人 | Candidate、Resume、Application、Tag、CandidateSource、WorkflowEvent | 一名候选人可投递多个岗位；简历和 AI 分析均保留版本与状态事件。 |
| AI 分析 | AnalysisTask、AnalysisResult、ModelInvocation | 任务异步执行，结果记录模型、版本、耗时、成本、依据和失败原因。 |
| 面试 | InterviewPlan、InterviewRound、InterviewFeedback | 一个申请可包含多轮面试；每份反馈关联面试官和评分表版本。 |
| Offer | Offer、OfferApproval、OfferTemplate、OnboardingRecord | Offer 发放前需通过配置的审批链；接受后生成入职归档。 |

所有流程实体使用不可变的状态变更记录。删除采用归档或软删除，避免影响审计和统计。

## 7. 招聘状态机

```text
需求草稿 -> 审批中 -> 已通过 -> 已导入岗位 -> 已关闭
                         |
                         v
岗位草稿 -> 说明书待确认 -> JD 待确认 -> 招聘中 -> 已暂停/已关闭
                         |
                         v
候选人导入 -> 分析排队 -> 已分析 -> 人工筛选
                                      -> 面试中 -> Offer 审批 -> Offer 已发放
                                      -> 已录用 -> 已入职归档
                                      -> 已淘汰
```

状态转移集中在后端领域服务中。每次转移必须校验前置状态、执行人权限与必填信息，并记录原因、时间和操作者。

## 8. CandiSift 集成

### 任务流

1. 招聘专员上传简历，业务 API 验证类型、大小和 ClamAV 扫描结果后写入对象存储。
2. 业务 API 建立 Resume、Application 和 AnalysisTask，并将任务写入 Redis 队列。
3. Worker 调用 CandiSift，传递经过授权的岗位资料和简历文本；服务返回结构化分析。
4. Worker 校验结果结构，写入 AnalysisResult 与 ModelInvocation，并更新任务状态。
5. 前端通过轮询或 Server-Sent Events 取得任务状态；完成后展示评分、依据、风险和建议问题。
6. 招聘成员人工确认筛选结论；系统记录结论与理由，不由 AI 自动改变候选人最终状态。

### 对接契约

- 业务 API 向 CandiSift 只传递任务 ID、岗位上下文、简历文件引用或文本、所选模型和回调标识。
- CandiSift 返回候选人结构化档案、维度评分、总分、优势、风险、面试建议、去重线索与处理元数据。
- CandiSift 不保存主业务流程状态；业务 API 是候选人与岗位关系的唯一来源。
- 调用失败使用指数退避重试；达到上限后任务进入失败队列，允许管理员或招聘专员手动重试。
- AnalysisTask 的权威状态存入 PostgreSQL。Worker 启动时重扫过期的排队和执行中任务，因此 Redis 重启不会遗失可恢复的分析任务。

## 9. 管理员后台与密钥管理

管理员后台是独立模块，不复用普通用户的“系统配置”弹窗。

### 管理能力

- 用户、部门、角色、审批链、面试评分表、Offer 模板和通知模板。
- 模型供应商、模型目录、默认模型、可用模型范围、调用限额和成本告警。
- 文件大小与类型限制、简历留存周期、招聘渠道和系统公告。
- AI 任务队列、失败任务、服务健康、审计日志和操作日志。

### 密钥规则

- 数据库、Redis、对象存储、JWT 签名和服务主密钥通过部署环境变量或 Vault/KMS 注入。
- 模型 API Key 如需通过后台录入，必须使用信封加密：密钥以应用数据密钥加密，数据密钥再由部署主密钥加密。
- 保存后只显示供应商、状态、创建者、更新时间和末四位；不得提供读取原文的接口。
- 测试连接由服务端发起，响应中不得回传密钥或供应商原始敏感报错。
- 所有新建、轮换、禁用和删除密钥的动作写入审计日志。

## 10. 部署与运维

首个生产环境使用 Docker Compose：

```text
Caddy/Nginx
  -> web
  -> api
  -> worker
  -> candisift
  -> postgres
  -> redis
  -> minio
```

- 反向代理终止 HTTPS，并限制上传大小与请求速率。
- PostgreSQL、MinIO 数据目录使用服务器持久卷；Redis 仅保存可重建的队列和缓存数据。
- API、Worker 和 CandiSift 提供 `/health` 与 `/ready`；反向代理和 Compose 使用健康检查。
- 数据库执行每日逻辑备份与定期恢复演练；对象存储采用版本或备份策略。
- 生产日志采用 JSON 格式，记录请求 ID、用户 ID、业务实体 ID 和任务 ID，不记录简历正文、密钥或完整个人敏感信息。

## 11. 质量与安全要求

- 账号使用安全密码散列、会话过期、登录限流和管理员操作二次确认。
- 文件上传校验 MIME、扩展名、大小和内容；下载通过短时授权 URL 或 API 代理。
- 审计覆盖审批、候选人状态、面试评价、Offer、密钥和导出操作。
- 关键业务接口具备请求校验、幂等键、统一错误格式和分页查询。
- 候选人数据导出需角色限制，并记录导出人、范围、时间与用途。
- AI 结果必须标注模型、版本、生成时间与“人工复核后使用”提示。

## 12. 迁移策略

1. 冻结现有页面的业务扩展，仅作为流程和内容参考。
2. 新建 Vue 前端与业务 API 基础工程，完成登录、角色、应用布局和审计基础能力。
3. 优先迁移招聘需求、审批、岗位说明书和 JD，验证模块边界。
4. 建立文件存储、候选人档案与 CandiSift 异步分析任务。
5. 迁移面试、Offer、入职归档、通知和报表。
6. 导入现有演示数据时，经过字段映射、清洗和人工抽样校验。
7. 在测试环境完成角色、流程、文件上传、AI 失败恢复和备份恢复验证后再部署生产。

## 13. 验收标准

- 不同角色无法访问或操作超出权限范围的页面与接口。
- 招聘需求到入职归档的每个状态转移都可追溯操作者、时间与原因。
- 简历上传后可查询 AI 任务状态，失败任务可安全重试，人工结论不被 AI 自动覆盖。
- 管理员可在不泄露密钥的前提下完成模型配置和连接测试。
- 服务重启后岗位、候选人、审批、文件索引和 AI 分析记录完整保留。
- Docker Compose 在干净服务器环境可启动全部服务，健康检查通过，HTTPS 与备份恢复流程可验证。
