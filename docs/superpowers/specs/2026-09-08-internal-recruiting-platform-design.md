# 内部招聘平台 V1 设计规格

## 1. 目标

将现有单页招聘流程演示重建为可在公司服务器稳定运行的内部招聘平台。系统服务公司内部招聘团队，覆盖招聘需求、审批、岗位与 JD、候选人、AI 简历筛选、面试、Offer、入职归档、运营报表和操作审计。

系统使用已获授权的 CandiSift 作为独立 AI 简历分析服务；主平台始终保有招聘流程、人工决策和业务主数据的控制权。

## 2. 范围

### 包含

- 内部账号登录、角色权限与管理员后台。
- 招聘需求申请、多级审批、撤回、驳回和审批记录；需求内维护编制数量、预算区间和目标到岗日期。
- 岗位说明书、JD 编辑确认、招聘状态与发布渠道管理。
- 候选人档案、PDF/DOCX/文本简历上传、来源、去重、标签和人才库。
- CandiSift 异步解析、脱敏、岗位匹配、评分、排序、分析报告和人工复核。
- 多轮面试安排、面试官反馈、评分表、面试结论。
- Offer 审批、模板生成、发放、接受/拒绝、录用文件输出和入职归档。
- 管理员配置模型、模型密钥、文件存储、邮件/短信、招聘渠道和 AI 调用限额。
- 招聘漏斗、渠道、周期、转化率和 AI 调用成本报表。
- Docker Compose 服务器部署、HTTPS 反向代理、健康检查、备份和审计。

### 不包含

- 薪酬、考勤、绩效、员工自助等完整 HRMS 功能。
- 自动淘汰候选人；任何淘汰、录用和 Offer 决定必须由有权限的人员确认。
- 将模型密钥暴露给浏览器或普通招聘成员。

## 3. 用户与权限

| 角色 | 核心权限 |
| --- | --- |
| 系统管理员 | 账号、角色、模型与密钥、渠道、存储、通知、全局审计和系统健康配置。 |
| HR 管理员 | 全流程查看，设置招聘流程和审批链，审批 Offer，查看报表。 |
| 招聘专员 | 创建需求、维护岗位、导入简历、发起筛选、安排面试和处理 Offer。 |
| 用人部门负责人 | 审批本部门需求、确认岗位说明书/JD、查看本部门候选人与面试结论。 |
| 面试官 | 仅查看被分配的候选人和面试材料，提交面试反馈。 |

服务端对每个动作校验角色、岗位归属和当前流程状态。前端按钮隐藏只用于改善体验，不能作为权限依据。

## 4. 页面与模块

前端使用 Vue 3、TypeScript 和 Vite。所有业务页面使用路由组织，页面不直接保存权威业务状态。

```text
src/
  app/                 应用壳、路由、权限守卫、布局
  modules/
    dashboard/         招聘概览与待办
    requisitions/      招聘需求与审批
    jobs/              岗位说明书、JD、发布渠道
    candidates/        候选人、简历、AI 分析、人才库
    interviews/        面试安排、反馈和评分表
    offers/            Offer、审批和入职归档
    reports/           漏斗、渠道、周期和成本报表
    administration/    用户、角色、模型、密钥、渠道和审计
  shared/              通用 UI、API 客户端、类型、格式化与错误处理
```

每个业务模块拥有 `pages/`、`components/`、`api/`、`types/` 和必要的 `stores/`。弹窗、表格和表单等纯界面组件位于 `shared/`；不得将流程规则写入可复用 UI 组件。

## 5. 后端与运行组件

业务后端使用 TypeScript 模块化单体，推荐 NestJS 搭配 Fastify。它提供认证、授权、参数校验、OpenAPI、后台任务投递和审计钩子。CandiSift 保持 FastAPI 独立服务。

```text
浏览器
  -> Web 前端
  -> 业务 API
        -> PostgreSQL       招聘业务数据、权限、审批、审计
        -> Redis            缓存、异步队列、限流
        -> MinIO / S3       简历与附件
        -> 通知适配器       邮件、短信、企业消息
Worker
  -> Redis                  获取可重建的任务投递
  -> PostgreSQL             领取任务、写入结果与审计
  -> MinIO / S3             申请任务范围内的短时文件访问
  -> CandiSift API          提交简历分析任务并接收结果
```

业务 API 是唯一可被前端调用的服务。前端不可直接调用模型供应商、对象存储或 CandiSift 的内部管理接口。

## 6. 核心数据模型

| 模块 | 主要实体 | 关键关系 |
| --- | --- | --- |
| 身份权限 | User、Role、Permission、Department | 用户归属部门并拥有角色；所有敏感操作写入 AuditLog。 |
| 招聘需求 | Requisition、ApprovalFlow、ApprovalStep、WorkflowEvent | 一个需求有一条审批流、多条审批记录和不可变状态事件；需求内含编制数量、预算区间和目标到岗日期。 |
| 岗位 | Job、JobSpec、JobDescription、PublishChannel、WorkflowEvent | 岗位来源于已通过需求；说明书与 JD 保留版本、确认记录和状态事件。 |
| 候选人 | Candidate、Resume、Application、Tag、CandidateSource、WorkflowEvent | Candidate 是跨岗位人才档案；Application 是候选人与岗位的一次申请关系，候选人可有多个 Application。简历和 AI 分析均保留版本与状态事件。 |
| AI 分析 | AnalysisTask、AnalysisResult、ModelInvocation | 任务异步执行，结果记录模型、版本、耗时、成本、依据和失败原因。 |
| 面试 | InterviewPlan、InterviewRound、InterviewFeedback | 一个申请可包含多轮面试；每份反馈关联面试官和评分表版本。 |
| Offer | Offer、OfferApproval、OfferTemplate、OfferDocument、OnboardingRecord | Offer 发放前需通过配置的审批链；OfferDocument 由已确认模板生成，含录用/任命文件；接受后生成入职归档。 |

Application 是招聘流程的状态主体，状态包括 `待分析`、`人工筛选`、`面试中`、`Offer 审批`、`Offer 已发放`、`已录用`、`已入职归档` 与 `已淘汰`。Candidate 仅有档案状态（有效、归档、隐私清除），不得因某个岗位的淘汰或录用改变其余 Application 的流程状态。

所有流程实体使用不可变的状态变更记录。常规业务删除采用归档或软删除，避免影响审计和统计；候选人隐私清除遵循第 11 节的数据留存规则，不适用仅软删除。

## 7. 招聘状态机

```text
需求草稿 -> 审批中 -> 已通过 -> 已导入岗位 -> 已关闭
                         |
                         v
岗位草稿 -> 说明书待确认 -> JD 待确认 -> 招聘中 -> 已暂停/已关闭
                         |
                         v
候选人档案创建/匹配 -> 创建职位申请

职位申请：待分析 -> 分析排队 -> 已分析 -> 人工筛选
                                           -> 面试中 -> Offer 审批 -> Offer 已发放
                                           -> 已录用 -> 已入职归档
                                           -> 已淘汰
```

状态转移集中在后端领域服务中。每次转移必须校验前置状态、执行人权限与必填信息，并记录原因、时间和操作者。

## 8. CandiSift 集成

### 任务流

1. 招聘专员上传简历，业务 API 验证类型、大小和 ClamAV 扫描结果后写入对象存储。
2. 业务 API 在同一 PostgreSQL 事务内建立 Resume、Application、AnalysisTask 和 `OutboxEvent`；OutboxEvent 使用 AnalysisTask ID 作为幂等键。
3. Outbox Dispatcher 将未投递事件写入 Redis 队列，并仅在队列确认后标记已投递；重复投递由任务幂等键去重。
4. Worker 以租约领取任务，定期写入心跳；仅 Worker 可调用 CandiSift，传递经过授权的岗位资料和短时有效的简历文件访问凭证或已提取文本。
5. Worker 校验结果结构，在事务内写入 AnalysisResult 与 ModelInvocation，并更新任务状态。`AnalysisResult.analysis_task_id` 具有唯一约束，状态更新使用租约令牌进行条件更新，重复执行只接受首个有效结果。
6. 超时租约由调度器回收；Dispatcher 定期重扫未投递 OutboxEvent，Worker 定期重扫过期的排队和执行中任务，确保 API、Redis 或 Worker 任一重启后任务可恢复。
7. 前端通过轮询或 Server-Sent Events 取得任务状态；完成后展示评分、依据、风险和建议问题。
8. 招聘成员人工确认筛选结论；系统记录结论与理由，不由 AI 自动改变申请最终状态。

### 对接契约

- CandiSift 仅加入 Compose 内部网络，不发布宿主机端口；浏览器与 API 均不可直接访问其接口。
- 仅 Worker 可使用轮换的服务凭证调用 CandiSift；V1 使用独立的长随机服务令牌，凭证只通过运行环境注入，带 key ID、过期时间和双令牌轮换窗口。后续可替换为 mTLS，不改变业务契约。
- 简历文件访问使用仅限当前任务、最小权限、短时失效的对象存储签名凭证；CandiSift 不获得存储桶的长期访问密钥。
- Worker 向 CandiSift 只传递任务 ID、岗位上下文、简历文件引用或文本、所选模型和回调标识。
- CandiSift 返回候选人结构化档案、维度评分、总分、优势、风险、面试建议、去重线索与处理元数据。
- CandiSift 不保存主业务流程状态；业务 API 是候选人与岗位关系的唯一来源。
- 调用失败使用指数退避重试；达到上限后任务进入失败队列，允许管理员或招聘专员手动重试。手动重试创建新的 OutboxEvent，但沿用 AnalysisTask 的幂等语义，避免重复写入结果。
- AnalysisTask 与 OutboxEvent 的权威状态存入 PostgreSQL。Redis 仅为可重建的传输层，不承担任务唯一存储职责。

## 9. 管理员后台与密钥管理

管理员后台是独立模块，不复用普通用户的“系统配置”弹窗。

### 管理能力

- 用户、部门、角色、审批链、面试评分表、Offer 模板和通知模板。
- 模型供应商、模型目录、默认模型、可用模型范围、调用限额和成本告警。
- 文件大小与类型限制、简历留存周期、招聘渠道和系统公告。
- AI 任务队列、失败任务、服务健康、审计日志和操作日志。

### 密钥规则

- V1 采用部署环境注入的专用主密钥作为信封加密根信任；该密钥不进入数据库、日志、镜像或浏览器。数据库、Redis、对象存储、JWT 签名和服务凭证同样仅通过部署环境注入；生产环境可将该主密钥替换为 Vault/KMS 管理而不改变数据格式。
- 模型 API Key 如需通过后台录入，必须使用信封加密：密钥以随机数据密钥加密，数据密钥再由主密钥加密。每条记录保存算法、主密钥 ID、主密钥版本、创建时间与加密载荷版本。
- 保存后只显示供应商、状态、创建者、更新时间和末四位；不得提供读取原文的接口。解密仅可发生在受授权服务进程内、发起供应商调用的最短时间内。
- 测试连接由服务端发起，响应中不得回传密钥或供应商原始敏感报错。
- 所有新建、轮换、禁用和删除密钥的动作写入审计日志。轮换时先写入新版本、执行连接测试并切换引用，再撤销旧版本；主密钥轮换后，后台任务使用旧主密钥解开数据密钥并以新主密钥重新包装，模型 API Key 的加密载荷不以明文落盘。主密钥不可用时，涉及解密的调用必须失败关闭、写入不含敏感信息的告警，并按受控恢复流程恢复同版本主密钥或从备份恢复，不得绕过加密读取密钥。

## 10. 部署与运维

首个生产环境使用 Docker Compose：

```text
Caddy/Nginx
  -> web
  -> api
  -> worker
  -> candisift
  -> postgres
  -> redis
  -> minio
```

- 反向代理终止 HTTPS，并限制上传大小与请求速率。
- PostgreSQL、MinIO 数据目录使用服务器持久卷；Redis 仅保存可重建的队列和缓存数据。
- API、Worker 和 CandiSift 提供 `/health` 与 `/ready`；反向代理和 Compose 使用健康检查。
- 数据库执行每日逻辑备份与定期恢复演练；对象存储采用版本或备份策略。
- CandiSift 只暴露给 Worker 所在的内部网络；网络策略拒绝其他容器访问其分析接口。对象存储服务凭证按服务拆分，Worker 仅能申请任务所需的短时文件访问凭证。
- 生产日志采用 JSON 格式，记录请求 ID、用户 ID、业务实体 ID 和任务 ID，不记录简历正文、密钥或完整个人敏感信息。

## 11. 质量与安全要求

- 账号使用安全密码散列、会话过期、登录限流和管理员操作二次确认。
- 文件上传校验 MIME、扩展名、大小和内容；下载通过短时授权 URL 或 API 代理。
- 审计覆盖审批、候选人状态、面试评价、Offer、密钥和导出操作。
- 关键业务接口具备请求校验、幂等键、统一错误格式和分页查询。
- 候选人数据导出需角色限制，并记录导出人、范围、时间与用途。
- AI 结果必须标注模型、版本、生成时间与“人工复核后使用”提示。
- 候选人隐私清除到期后，删除原始简历、附件、提取文本、AI 分析结果、向量与搜索索引，并使短时下载链接立即失效；只保留无法反推身份的审计汇总、流程时间线与统计聚合。法律保全记录可暂停指定候选人的清除，并记录依据、批准人和到期复核时间。
- 备份中的候选人数据遵循独立且明确的保留期限；到期备份须不可恢复地删除。恢复备份后，清除任务必须优先重放，防止已清除的候选人数据重新长期可见。

## 12. 迁移策略

1. 冻结现有页面的业务扩展，仅作为流程和内容参考。
2. 新建 Vue 前端与业务 API 基础工程，完成登录、角色、应用布局和审计基础能力。
3. 优先迁移招聘需求、审批、岗位说明书和 JD，验证模块边界。
4. 建立文件存储、候选人档案与 CandiSift 异步分析任务。
5. 迁移面试、Offer、入职归档、通知和报表。
6. 导入现有演示数据时，经过字段映射、清洗和人工抽样校验。
7. 在测试环境完成角色、流程、文件上传、AI 失败恢复和备份恢复验证后再部署生产。

## 13. 验收标准

- 不同角色无法访问或操作超出权限范围的页面与接口。
- 招聘需求到入职归档的每个状态转移都可追溯操作者、时间与原因。
- 简历上传后可查询 AI 任务状态，失败任务可安全重试，人工结论不被 AI 自动覆盖。
- 管理员可在不泄露密钥的前提下完成模型配置和连接测试。
- 候选人投递多个岗位时，各职位申请的筛选、面试、Offer 和淘汰状态相互独立，候选人档案不被单个职位流程错误覆盖。
- 在 API、Redis 或 Worker 任一进程于任务创建期间异常重启后，Outbox Dispatcher 与任务租约机制能够恢复任务，最终至多写入一份有效分析结果。
- CandiSift 无公开端口，且只有持有有效服务凭证的 Worker 能提交任务；其无法获得对象存储长期密钥。
- 简历留存到期后，生产数据、衍生分析数据和到期备份均按规则清除，法律保全记录可审计。
- 密钥记录包含加密版本信息；完成轮换后新调用使用新版本，主密钥不可用时服务不得降级为明文或返回密钥。
- 服务重启后岗位、候选人、审批、文件索引和 AI 分析记录完整保留。
- Docker Compose 在干净服务器环境可启动全部服务，健康检查通过，HTTPS 与备份恢复流程可验证。
