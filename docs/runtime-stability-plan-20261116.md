# 本地运行稳定性优化方案

日期：2026-11-16。状态：已实施只读预检、稳定产物、托管入口与隔离验证；业务恢复仍受数据核对阻断。

最新执行记录见 [恢复方案执行记录](./recovery-execution-20261116.md)。正式五项修复入口、较新时间保留及 23 项维护衔接已实现并通过隔离验证；当前 D 盘严重缺空间，四个简历原件仍待补齐，业务迁移和完整启动尚未执行。下文早期两迁移范围和运行快照仅作问题来源，不是当前审批或验收结果。

用户已要求在核对备份、数据路径和在途任务后执行两项迁移。本轮检查发现旧公共表与公司表冲突、对象路径不完整，尚不满足这些前置条件，因此没有迁移业务库、切换公司路由、改写业务配置或停止已有业务 Worker。业务 API 尚未恢复。实施状态与操作步骤见 runtime-operations-20261116.md；下文保留总体设计及目标，不能把全部目标视为已验收。

## 一、问题依据

- 原 scripts/start-all.mjs 通过独立 cmd /k 窗口启动服务，退出后不跟踪服务进程。窗口存在不等于业务进程存在。现已替换为稳定实例控制器。
- 日常启动调用 start:dev，先构建后再调用会重复构建的 API start，重启受到工作区代码变化影响。
- applySourceModeDefaults 会改写已有 .env 的部分数据库、存储与 Worker 配置，混淆初始化和普通启动。
- 当前有效配置缺少 TENANT_SCHEMA_ROUTING=on，启动检查立即拒绝；仅为检查进程临时启用后，发现业务库尚缺 0101、0102 两项迁移。
- 公司 Schema 结构检查通过，但未比较旧公共表与公司表的数据，不能据此直接切换数据路径。
- API health 主要判断进程响应；ready 中部分能力仅核验配置，不能证明实际调用可用。
- 启动器依服务名判断能否复用进程，不校验实例、发布版本和数据路径；端口冲突时自动选择其他端口。
- check-saas-local-health.mjs 只检查部分历史迁移，不能代替当前发布完整性检查。

上述证据能说明当前新版为什么启动失败，不能确定历史进程第一次退出的时间与原因。

## 二、总体设计

保留现有 API、Worker、Web、PostgreSQL 和模型服务，不把全面重构或强制迁移容器作为修复前提。

分离两个入口：日常运行只负责已验收版本的 start / stop / status / doctor / logs；版本发布负责构建、测试、备份核验、批准后迁移和切换。当前已实现 runtime:prepare、runtime:start、runtime:stop、runtime:status、runtime:doctor、runtime:logs；重新启动采用显式 stop 后 start，不提供自动迁移或强制接管。

普通启动流程：实例排他锁 -> 有效配置校验 -> 数据库与存储预检 -> 启动 API/Worker -> 启动 Web -> 同源代理及版本核验 -> 输出真实状态。

日常启动不得编译、迁移、seed 或改写配置；缺少结构时不得关闭隔离或绕过发布检查。

## 三、配置治理

- 初始化、配置修改和普通启动独立；普通启动只读 .env，不自动补值、换存储或调整数据库端口。
- 复用既有解析逻辑，统一配置来源和优先级；API、Worker、检查工具共享同一份有效配置。
- 核验 API/Worker 公司路由、数据库目标与存储位置一致；缺失或冲突时指出键名、配置来源及修复步骤。
- 配置修改先校验，再原子替换，并保留受限权限备份。诊断只输出非敏感摘要，不能泄露凭据或业务正文。
- 已有业务库不能启动时默认开启公司路由。首次切换必须核对历史数据、在途任务及全部写入者；新空环境可走单独初始化流程。

## 四、稳定版本与发布

- 独立发布目录包含 API、Worker、静态 Web、共享运行依赖及对应 SQL 清单；记录版本、文件摘要、运行时要求和配置契约。
- 不引用可变源码目录的 SQL 和共享包，编辑代码不影响已验收版本重启。独立目录需验证环境文件与迁移路径解析正确。
- 复用现有静态 Web 服务及代理实现，不用 Vite 开发服务器承担长期业务访问。
- 构建只在候选目录执行；普通启动直接运行预构建程序。status 显示实际运行版本，不以工作区版本冒充。
- 切换 production 模式前核验 Cookie、访问源、代理、WebSocket、密钥及存储路径，不只修改 NODE_ENV。
- 涉及迁移或数据路径变化的升级须批准范围和维护窗口，暂停写入、排空 API/Worker 后台任务，确认没有遗留写入者。
- 备份包括数据库、对象文件、配置及独立保管的加密密钥，验证可恢复后才执行获准迁移。
- 保留现有迁移事务和锁；迁移失败停止发布，启动器和看门狗永不自动修库。
- 只有数据库兼容才允许回切旧程序；存在不兼容迁移或新写入时，采用另行批准的恢复方案，不能盲目降级。

## 五、后台托管与恢复

- 稳定运行独立于 Codex 和命令窗口，采用 Windows 后台托管入口，并由系统服务机制负责托管器自身的启动恢复。
- 优先接入成熟进程管理实现，先验证本机 Windows、Node、Python 兼容性，不自行重写完整进程管理平台。
- 一个实例只有一个管理者，记录实例 ID、PID、启动时间、执行路径和版本；停止时校验身份，只操作本实例进程树。
- 业务端口固定为 API 3100、Worker 4001、Web 5174；冲突则报告占用身份，不悄悄换端口。开发模式可另行使用动态端口。
- 只有实例、版本和配置摘要匹配才复用现有服务；不能仅按服务名称认领。外部已有模型服务只检查，不擅自停止。
- API 与模型服务分开托管，避免重启 API 触发模型反复加载。
- 配置、迁移、隔离和版本错误进入 BLOCKED，不循环重启；使用稳定错误码，如 CONFIG_INVALID、DB_MIGRATION_REQUIRED、RELEASE_MISMATCH。
- 意外退出先留存退出码和日志，复核安全前置条件后有限重启。建议退避 2、5、15、30 秒并加入抖动，十分钟失败五次熔断；参数由演练调整。
- 短暂数据库故障优先有界重连并暂停领取任务，不因一次探针超时立即杀进程。
- 停止先拒绝新写入，再排空任务并释放资源；超时报告未完成工作，不假称排空成功。
- 逐类验证任务租约、幂等及恢复。支付、邮件和模型调用结果不确定时不自动重放，保留核对流程。

## 六、健康检查与反馈

- health 表示进程响应；ready 检查核心依赖，核心不可用返回 503。启动时做完整预检，运行期探针缓存、限频且有明确超时。
- 核心检查包含数据库、发布契约、公司数据路径和关键存储；不能每秒重复整套 Schema 审计。
- status 汇总 API、Worker、Web 同源代理、数据库及能力状态，记录检查时间、版本、重启次数和错误码。
- LLM/OCR 配置存在只能标 configured，不能标 verified；连接、模型加载及实际任务成功分别表示。
- 分开“核心可用”“能力降级”“启动阻断”；只有部署声明的全部必需能力通过才报告完整运行。
- OCR/语音不可用仅阻断对应能力，不拖垮不相关页面；受影响任务明确拒绝或排队，不能伪装成功。
- 从 Web 同源入口验证 API ready，并检查 API/Worker 版本匹配；不能只请求首页或单独 health。
- 前端显示明确服务不可用状态和重试入口，保留未提交输入，不循环重放写请求。
- 详细诊断仅本机或受权管理员可见，普通页面不暴露凭据、数据库目标和内部路径。

## 七、日志与诊断

- 按实例、服务、启动批次集中记录 stdout/stderr，包含版本、启动/退出时间、退出码和最后就绪时间。
- 日志脱敏、轮转、限制总大小并制定保留期，避免长期运行填满磁盘。
- doctor/status 只读且快速退出，提供中文摘要和 JSON；明确错误尽早报告，不仅等待固定超时。
- 修订旧运维脚本，复用当前检查契约，移除依赖少数历史迁移推断健康的逻辑。

## 八、实施顺序

1. P0，本次恢复：批准维护范围 -> 核对目标和实际对象存储 -> 备份恢复验证 -> 暂停全部写入者 -> 核对历史公共表与公司数据及在途任务 -> 获准执行 0101/0102 -> 统一配置 -> 完整检查 -> 启动及端到端验收。有数据差异先制定增量切换方案，不直接覆盖。
2. P1，防止误判：统一预检、错误码和 status；普通启动不改配置、不执行维护动作；稳定端口、进程身份和集中日志；同源代理验收。
3. P2，稳定运行：独立稳定产物、预构建启动、静态 Web、后台托管、有限重试、熔断与优雅退出，验证脱离终端仍运行。
4. P3，发布闭环：候选版本、备份核验、批准迁移、受限回退、任务恢复和长期故障演练。未经真实恢复验收不宣称无损恢复。

本轮仅在随机专用 PostgreSQL 和合成数据上验证，不修改实际业务库，不代替写入冻结、当前备份恢复、原密钥核验及业务冒烟，也不构成长期运行验收。

## 十、验收标准

以下为拟实施后的要求，不是本轮已通过的结果。

| 场景 | 必须满足 |
| --- | --- |
| 配置缺失、API/Worker 路径冲突 | 启动前明确阻断，不改配置、不迁移、不开始业务写入 |
| 缺迁移、未知版本、公司结构损坏 | BLOCKED，不关闭隔离、不无限重试 |
| 重复/并发启动，端口被其他项目占用 | 不产生重复消费者，不停止其他项目，不自动换业务端口 |
| 关闭 Codex 或启动终端 | 核心服务继续运行，状态可独立读取 |
| 杀死 API | 满足安全前提时目标 60 秒内恢复；退出与重启证据完整 |
| 数据库故障与恢复 | ready 返回 503，领取任务暂停；不写错公司，恢复后有界重连 |
| 连续崩溃 | 熔断，保留证据，不形成资源或模型重载风暴 |
| OCR/语音故障 | 核心和能力状态准确分开，受影响任务明确反馈 |
| 编辑工作区代码或 SQL | 稳定版本重启行为不受影响，显示真实运行版本 |
| Web 正常但代理断开 | 页面和 status 反映故障，不报告完整成功 |
| 维护迁移失败 | 不启动新写入者，不盲目撤销已提交迁移 |
| 备份恢复、对象或密钥缺失 | 隔离目标验证，缺关键材料拒绝冒充恢复成功 |
| 授权业务冒烟 | 登录、公司切换和关键流程通过，不真实发信或收付款 |
| 持续运行 | 先 24 小时再观察 72 小时，记录内存、句柄、连接、磁盘和任务积压趋势 |

单元测试覆盖状态机和副作用边界；随机独立数据库覆盖结构、迁移和故障；浏览器验证代理、错误状态及授权业务流程。恢复时间、性能和长期稳定性需实测，不以健康接口通过代替。
