# 简历语义评分与证据边界

## 执行链路

- 生产 PostgreSQL 模式下，已有岗位要求的简历评分由 AI Worker 执行。API 的同步处理入口保持任务排队，不再内联产出关键词匹配分数。
- 有岗位专属评分 Skill 的任务仍只允许 AI Worker 处理，保留规则快照。
- Worker 配置完整的 OPENAI_BASE_URL、OPENAI_API_KEY、OPENAI_MODEL 后默认使用 OpenAI-compatible 模型。WORKER_USE_LLM_ANALYSIS=false 可以显式关闭调用，但岗位评分会明确失败，不会退回关键词算法。
- 数据库任务轮询需 WORKER_DB_POLL=true。没有岗位要求且没有 Skill 时，只做解析，不调用模型、不生成匹配分数。
- NODE_ENV=test 的内存仓库保留规则模拟，用于既有工作流测试；不代表生产评分链路。

## 语义规则

模型完整读取本次脱敏简历，逐项对照已确认的岗位要求。支持同义表达、同等工作行为，不能单看关键词；必须考虑否定、实际工作主体、时间和职责深度。

| 状态 | 含义 | 证据与分数 |
| --- | --- | --- |
| met | 有直接证据支持满足 | 正分，附简历原文 |
| partial | 只支持部分要求，例如协助而非独立负责 | 正分但不能满分，附简历原文 |
| not_mentioned | 没有足够直接证据 | 0 分、无正面引用、待人工核实，不认定具备也不认定明确不符合 |
| contradicted | 简历明确表达与要求不符 | 0 分，必须附明确反证 |

例如：
- “统计每月出勤数据，核对请假和加班记录”可支持考勤管理，不要求出现完全相同关键词。
- “协助办理入职、离职手续”能证明参与，但不能直接证明独立负责整个流程。
- “维护员工档案”不能证明执行了保密制度。
- “提交薪资核算基础表格”不能证明独立核算薪酬。
- 人事助理的职位名称不能证明具备招聘经验。

## 服务端校验

每条岗位要求必须恰好返回一次，禁止遗漏、重复或增加 ID。正面和冲突判断的引用必须出现在本次实际发送的脱敏文本中，仅允许 Unicode/空白归一化；伪造引用、未提及却给分、非法分数等均判为模型响应无效，任务失败，不使用旧算法或默认分数兜底。

总分由服务器重算，不直接保存模型裸总分：
- 默认岗位规则：硬性要求权重 2.5，其他要求权重 1，加权平均并四舍五入。
- 专属 Skill：逐维度校验状态、原文、得分和满分，按 sum(score)/sum(maxScore)*100 汇总。
- 自由文本 Skill 的维度与权重由模型解释，服务器校验合法性及求和，不能确定性证明模型完整、准确解释了所有自由文本规则；重要规则应结合快照人工检查。

展示用总结由已校验分项生成，不直接采用模型自由填写的优势和总结。前端区分部分满足、待核实、明确不符，显示模型来源、分项分数与引用。超过 100,000 字符的脱敏简历明确失败，不静默截断。

原文引用校验能防止伪造证据，但不等于自动证明引用与要求的语义相关，也不核实简历事实真实性。语义判断仍可能误判，需要人工复核。不会自动淘汰、录用或发 Offer；AI 40% + 人工 60% 的规则不变。

## 启用与历史结果

修改代码后重新构建并重启 API、Worker，前端重新构建/刷新。确认模型配置及数据库轮询已开启后，重新解析指定简历，才会生成新版本语义报告。

不会批量重评分或覆盖历史报告、人工评分、候选人状态。本次实现测试使用模拟模型响应；真实模型连通性检查只使用无个人信息的合成简历，不写业务数据库。

## 无分问题排查与岗位版本归属修复（2026-10-09）

“解析完成”不一定代表岗位评分已生成。没有已确认岗位要求且没有评分 Skill 时，仅生成简历解析报告，AI 分数为空而不是 0。

本地发现岗位说明书/JD 创建时未写 organization_id，数据库默认将其写入历史迁移工作空间，导致 Worker 同企业查询无法读到岗位要求。现已调整为：

- 新说明书和 JD 从父岗位继承企业归属，内部无企业作用域的写入也不能落到错误的默认企业。
- 有企业作用域的读取、创建、确认版本均验证父岗位归属；列表不返回其他企业内容。
- API 和 Worker 检测到已确认的跨企业关联版本时，明确返回 JOB_ANALYSIS_CONTEXT_SCOPE_MISMATCH，不再把异常当成“没有岗位要求”。
- 分数为空时，界面明确展示 AI 评分未生成及本次报告原因；最终分显示“待 AI 评分”，不误导为仅待人工评分。真实的 0 分仍可正常人工复核。

历史错误记录不能通过移除企业过滤来读取。提供单岗位、默认只读的修复脚本 scripts/repair-job-version-scope.mjs：先传入已核实的岗位 UUID 检查，再按需添加 --apply。脚本只处理历史工作空间的关联版本，要求创建人、创建时间和父岗位企业成员关系均能核实；不重分配其他真实企业的记录。更新在事务内完成并写入 audit_logs，记录原企业、新企业、版本 ID 和内容哈希；不修改版本正文、确认时间、历史分数或人工评价。

此次仅修复用户反馈的人事岗位的一个说明书版本和一个 JD 版本，后台已验证可读取 5 条任职要求及 8 项技能要求。其他岗位的历史异常未批量修复。

新增回归验证：API 全套 280 项通过、9 项外部依赖测试跳过；另外使用本地 PostgreSQL 真实执行岗位版本隔离事务测试 1 项通过（所有测试数据回滚）；Worker 48 项通过、3 项跳过；候选人前端 65 项通过，类型检查和前端构建通过。当前模型配置最小请求已返回 HTTP 200；完整简历评分结果以本次实际任务为准，不以连通性测试代替业务评分验证。


完整业务链路补验已成功：只为用户反馈的王强/人事岗位申请新建一次重新解析任务，使用当前配置的模型 gpt-6.1-sol；首次执行即完成并保存语义评分 52/100。13 项要求中，5 项满足、4 项部分满足、4 项未提及、0 项明确不符；未提及项均为 0 分且无引用。已通过候选人详情服务确认最新申请投影采用这条 52 分报告，人工分和最终分仍为空，历史 27 分报告未覆盖。API 与 Worker 在数据修复后已重启并通过健康检查；最后将 API 归属异常检查从通用版本列表调整到评分入口的防御性优化已构建测试通过，但再次重启被执行策略拦截，需下次正常重启 API 时加载，不影响此次已保存的 52 分结果。浏览器验证只到开发环境登录页，未绕过认证，因此未声称验证了登录后的实际详情页；评分展示逻辑由候选人前端回归测试覆盖。

## 全量岗位关联修复与版本号冲突（2026-10-09）

用户补充后端工程师岗位截图，错误为 PostgreSQL `23505 / job_spec_versions_job_id_version_key`。全库检查发现还剩 3 个岗位、4 条历史企业归属异常：当前业务企业的后端岗位有说明书和 JD 各一条，另两个岗位来自旧的 `resume-score-integration-test` 测试企业，各有一条说明书。后者经核实：企业 kind=test、无成员、岗位编号为 JOB-UUID、无人工创建人，只有固定名称的评分联调候选人及其自动 profile_parsed 事件，没有申请、简历或解析任务。

本次已将全部 4 条记录恢复到各自父岗位的企业，未将不同企业的数据统一分配到当前企业。使用升级后的 `scripts/repair-job-version-scope.mjs --all --include-test-fixtures` 先只读检查，再加 `--apply` 执行；所有更新及 3 个岗位审计在同一事务内，逐行验证正文 SHA256 和确认时间不变。遇到真实其他企业记录或归属证据不足会整笔拒绝，不做自动猜测。审计请求 ID：`job-version-scope-repair-dda8e65a-93e2-445f-bff6-9435b1cf22c7`。

修复后再次全量 dry-run 为 0 个岗位、0 条记录；独立 SQL 复查返回空异常列表。12 个现存岗位全部通过带各自企业作用域的评分上下文检查。后端工程师 `2810aa4c-6bc9-4d95-872a-5303960c88ce` 的详情服务已正常返回说明书 v1 和 JD v1，均保持已确认状态。候选人、评分、人工评价和申请状态没有变更，没有批量重评分。

版本号冲突的直接原因：业务服务先读取经过企业隔离的版本列表，再计算 max+1。历史归属异常使列表为空，服务提交第 1 版，而数据库中的 `(job_id, version)` 唯一键已经存在；并发保存也可能计算出同一个版本号。真实 PostgreSQL 回归测试在修复代码前复现了与截图相同的 23505 及约束名。

已将数据库模式的说明书/JD 创建改为由 Repository 在事务中锁定父岗位后分配下一版本号，使用该岗位全部既有版本的编号，不读取或返回隐藏正文。说明书 JSON 中的 version 也采用实际分配值，避免元数据与数据库版本不一致。保留企业读取和确认过滤。
