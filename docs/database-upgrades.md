# 数据库升级与 API 发布

数据库迁移负责保存新版功能需要的表、字段、索引与触发器。本文是维护操作说明，不是迁移授权；2026-11-13 本轮只在随机独立测试库验证，未对业务库运行 db:migrate 或 deploy:api。

## 在仓库中发布新版 API

先确认目标数据库、当前运行版本、备份及维护窗口。连接仍沿用 DATABASE_URL 或 PGHOST、PGPORT、PGDATABASE、PGUSER、PGPASSWORD 及既有环境文件加载规则。以下构建与检查不会执行迁移；检查仍可能连接真实配置中的库，因此本轮未对业务库执行：

```powershell
pnpm --filter @smartrecruit-pro/api build
npm run db:status
npm run db:check
node scripts/check-postgres-ready.mjs
```

- `db:status`：只读检查，显示目标数据库、已执行数量以及待执行文件，不创建迁移记录表。
- `deploy:api`：检查 API 构建产物，设置生产环境，执行仓库中全部尚未应用的迁移；全部成功后以前台方式启动 API。不自动构建或运行开发种子。
- `db:check`：只读迁移清单检查；连接失败、迁移名称冲突、未知数据库版本或待执行迁移时返回非零；不等于完整结构检查。
- `node scripts/check-postgres-ready.mjs`：只读启动检查，除迁移清单外还校验关键列、活跃公司结构及已登记文件位置；不迁移、不修复、不 seed。
- `db:migrate`：只执行迁移并退出，适合由进程管理器或容器平台另行启动 API 的环境。

`deploy:api` 和 `db:migrate` 都是须单独批准的维护入口。前者会执行整个迁移目录中全部待执行文件，成功后启动 API，而非只升级某一个功能。先用 `db:status` 核对范围；这些入口依赖已构建的 API 数据库模块。

`deploy:api` 不会停止已经运行的 API。已有实例应由原有进程管理器按发布流程停止或切换，避免新实例占用相同端口。API 启动后会持续占用当前终端，信号与退出状态由现有生产启动脚本传递。

## 普通重启与容器部署

`npm start` / `npm run start:production` 只启动已构建 API；`start:dev` 也不再隐式迁移。API 正式启动及开启数据库轮询的 Worker 在监听/领取前做只读检查，异常拒绝启动。开发 seed 仍需既有 NODE_ENV=development 与 ALLOW_DEV_SEED=true 双条件，不是默认重启行为。

检查要求 TENANT_SCHEMA_ROUTING=on；缺少结构时不得关公司路由或回退 public。低层 createApp/createHttpServer 是装配与测试入口，不自行执行启动检查；业务入口应使用 startServer，手工装配程序必须先调用检查。

只有目标环境、备份及维护窗口得到批准后，才可在有仓库、依赖和构建产物的维护环境执行：

```powershell
npm run db:migrate
npm run db:check
node scripts/check-postgres-ready.mjs
# 检查通过后，由现有发布工具启动或切换新版 API / Worker
```

当前 API 镜像不打包维护脚本和 SQL；API/Worker 运行期检查需要 /app/db/migrations 清单。Compose 已明确将仓库 db/migrations 挂载为该位置的只读卷；非 Compose 部署须提供对应版本的只读目录。没有放开 .dockerignore 的 SQL、环境配置或备份排除。缺失目录或清单为空会拒绝启动，不能以关闭检查代替。

Compose 已取消把 SQL 目录挂载到 PostgreSQL 的 docker-entrypoint-initdb.d。旧做法会直接执行 SQL，却没有建立迁移账本，新版只读检查会拒绝这种结构。取消挂载只影响未来新卷初始化，不会修改现有数据卷；普通容器启动仍不运行迁移。

全新空卷的维护顺序是：批准目标及操作范围，先只启动 PostgreSQL；从有仓库、依赖和 API 构建产物的维护环境指向该新库，显式执行 db:migrate，再执行 db:check 和完整只读检查，成功后才启动 API/Worker。运行镜像不带维护入口，不能直接假定在 API 容器里执行上述脚本可用。空库未经维护初始化时，API/Worker 拒绝启动是预期防护，不是自动建表入口。

如果旧初始化方式已创建业务表却没有账本，不得直接重跑全部 SQL，也不得按文件数量伪造已执行记录。先保全备份，在独立恢复目标核对真实结构、历史版本及约束；形成单独批准的基线恢复方案后才能接入。本轮没有为旧库自动补账、构建或启动新容器。

维护迁移器增加 MIGRATION_BASELINE_REQUIRED 防护：当前目标 Schema 存在非扩展自带的表、视图、物化视图、外部表或序列，但账本缺失或没有任何版本记录时，在建账本和执行 SQL 前拒绝。该检查不是旧库基线修复器，也不证明仅包含函数等其他对象的 Schema 是全新空库；不应据此放行来源不明的历史库。

运行镜像文件清单同时补齐 enterprise-ai/index.js 静态导入的 billing.js 和 errors.js；新增递归依赖清单测试。该测试只验证源码打包清单，不代替镜像构建、启动或漏洞扫描。

## 失败、重试与并发

每个迁移文件单独使用事务；失败文件的 SQL 和迁移记录一起回滚，先前成功文件保留。修复失败原因后再次执行，会跳过已完成文件。迁移失败或被中断时，发布入口返回失败，不会继续启动新版 API；已经运行的服务仍由原有进程管理器管理。

迁移器用 PostgreSQL advisory lock 串行执行并发升级，记录保证同一版本不重复执行。同版本不同名称、数字等价的重复文件名及数据库出现本地没有的未来版本均拒绝。已应用 SQL 不修改或改名，变更新增版本；运行中断不撤销之前成功的升级。

当前没有历史 SQL 内容 checksum；关键表列及公司 structure_ready 校验也不等于所有外键、索引、触发器均完整。未知历史文件位置不由启动检查补登记。门禁是必要条件，不是完整数据库审计或迁移安全证明。

## 本轮新增与兼容边界

| 文件/版本组合 | 影响与处理 |
| --- | --- |
| 0099_object_write_intents.sql | 新增公共写入意图、租约索引，给 interview_stored_objects 增 physical_key 及非空唯一索引；不推断历史位置 |
| 0100_object_deletion_fences.sql | 新增公共删除墓碑、引用防护函数，在 public 及已登记公司 resumes/interview_audio_recordings 安装触发器；公司数量影响 DDL 时长 |
| 新服务 + 缺迁移/损坏公司 | 正式启动拒绝；先排查并在批准窗口升级，不降级到公共业务表 |
| 新服务 + 当前完整结构 | 随机空库/多公司及并发只读检查通过，实际历史业务数据兼容仍未验收 |
| 旧服务 + 0099/0100 后结构 | 不作为兼容组合放行：旧写入/删除路径可能绕开新状态机，触发器或位置约束也可能拒绝旧写入；禁止新旧写入者混跑 |
| 无账本、未知未来版本、改名记录 | 只读检查失败，不自动补账本、修复或跳过 |

新增索引不是 CONCURRENTLY，ALTER TABLE 和 CREATE TRIGGER 会获取锁。维护前评估真实表量、活跃事务与锁等待，先停新写入并排空 API/Worker；在隔离历史夹具测耗时，不能照搬合成空库时间。按目标环境批准的锁/语句超时执行，超时先调查阻塞，不能无界重试。

迁移前备份必须分别包括数据库、实际对象文件、配置及独立保管的加密密钥，并记录备份后的增量。不要把密钥与数据库 dump 混为一份可分享产物。升级中失败先停止新版写入，保全迁移状态和日志；数据库已部分升级时不直接重启旧版。需要恢复时，在新恢复目标校验数据库、对象及密钥，处理备份后的新增数据后再切换，不能承诺无损或简单 SQL 降级。

## 本次验证范围

发布脚本替身覆盖迁移成功后启动、失败/中断停止及缺构建产物提前失败。本轮真实 PostgreSQL 使用本机 15479 独立实例中的随机 reliability_verify_/schema_verify_ 数据库；支付、迁移、发布检查共 10 组通过，另有双 API、三 Worker 和浏览器验证。随机库完成后删除，不使用旧文档中的固定业务/测试库名称。

新增检查在 default_transaction_read_only=on 下验证结构缺失、未建公司、公司列损坏、存储位置变化、待迁移与未来版本均被拒绝，并发检查不改迁移账本。合成 pg_dump/pg_restore 校验数据库/对象散列、配置及密钥缺失/错误/跨公司拒绝和正确密钥恢复；真实密钥与完整业务备份恢复未验收。完整证据与未完成项见 ordered-optimization-progress-20261113.md。

业务数据库迁移和业务服务发布需在实际发布时执行；修改这些脚本本身不会升级当前业务环境。
